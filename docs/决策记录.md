# 决策记录（Pek.ZDsMallUI · Zig）

## 2026-11-19 采用 Zig 完全迁移 DsMallUI（首版）

**用户原话**：「G:\Code\Pek.FrameWork\Pek.DsMallUI和G:\Code\Rust\Pek.DsMallUI帮我参考这两个项目使用zig完全迁移实现UI库功能。」

**决定**

1. 以 **Rust 版为行为基准**、以 **C# 版为契约（路由/字段/文案/目录）** 迁移到 Zig；
2. 公共能力全部复用 `zzig`（Web 栈 / Value 模型 / 日志 / 文件 / 时间 / 出网），本仓库只写 DsMallUI 特有部分；
3. 新增两处公共库缺口（`multipart` 解析、C# 口令互通）先在本仓库落地，并在模块注释写明
   「若出现第二个消费方就下沉进 zzig」；
4. 后台持久化用 `AdminBackend` vtable 注入（对齐 Rust 版），示例用内存实现。

## 2026-11-19 控制器拆分：一控制器一文件（对齐 C#）

**用户原话**：「每个控制器一个zig文件吧，和C#一样的」

**决定**：`HomeController.zig` / `ConfigController.zig` / `LoginController.zig` /
`UploadController.zig` 各一文件；共享的区域上下文与挂载抽到 `AdminArea.zig`（对应 C# 区域公共部分）。
**放弃**单文件 `admin.zig` 聚合写法（可读性差、与 C# 目录不对应）。

## 2026-11-19 目录改为 C# 同构（`Areas/`）

**用户原话**：「我记得C#的区域是会有Area这种文件夹的」

**决定**：视图与控制器搬进 `Areas/Admin/{Controllers,Views}`、`Controllers/`，共享视图留 `Views/Shared/`。
**代价与处理**：Zig 的 `@import`/`@embedFile` 不能跨模块根目录，因此
**模块根文件必须放仓库根**（`pek_zdsmallui.zig`），`build.zig` 的 `addModule` 指向它；
`@embedFile` 直接引用 `Areas/…`、`Views/…`、`assets/…`，**删掉了两个只为嵌入而生的中间模块**。

## 2026-11-19 下载改走 fallback 而不是中间件

**现象**：`GET /Upload/downloads/images/...` 返回 404。
**根因**：zzig 路由器**只在实际命中路由（或设置了 fallback）时才执行中间件**；深路径没有任何路由能匹配。
**决定**：`UploadController.mount` 注册 `app.router.fallback`，顺序为
「上传目录下载（加 `Content-Disposition`）→ `app.statics`（wwwroot）→ 404」；
这样既覆盖深路径，又不改变 `App` 原有的静态资源行为。

## 2026-11-19 视图两处改写（Razor 子集约束）

1. **`@{ // 注释 }` → `@* ... *@`**：zzig 代码块只认 `var x = ...;` 与 `Layout = "...";`，`//` 注释会解析失败。
2. **设置页内联 JS → 静态文件**：`@section` 体内遇到 `}` 即结束块，内联函数体的花括号会被误判；
   改为 `assets/admin-config.js`（并在 `materializeDefaults` 首次落地到
   `wwwroot/static/admin/js/admin-config.js`）。
   同时把原生 `window.alert` 改为就地提示（全局「禁止原生弹窗」口径）。

## 2026-11-19 口令默认 `md5+sha1`

对齐全局「登录口令规范」A 档（有 HTTPS 的面板）：存储 `$md5+sha1$…`，后端同时接受
明文与「前端先 MD5」；`sha512` 档只认明文，故选 `md5+sha1` 作为 `password.zig` 的默认算法
（C# 默认 `sha512`，此处按生态口径覆盖，并在 `docs/移植对照.md` 记录）。

## 2026-11-19 抓取扩展名按 URL 推断

`zzig.Http` 的响应不带响应头，无法按 `Content-Type` 猜扩展名 →
按 URL 末段推断、无扩展名时 `.jpg` 兜底（Rust 版按 Content-Type 猜）。
换来的是 **20 秒超时保护**（远端挂死不会拖住请求线程），已在移植对照标注。

## 2026-11-19 登录 / 退出登录 + JWT（复用 Pek.ZPermissions，远端仓库接入）

**用户原话**：「https://github.com/RemoteAll/Pek.ZDsMallUI 这个是仓库地址，另外你要帮我参考实现登录和退出登录的功能，同时登录时要把JWT同样带上」

### 为什么这样实现

- **不自己写 HMAC**：生态里已有 `Pek.ZPermissions`（Zig，HS256，与 C# `NewLife.Web.JwtBuilder`、
  Rust `Pek.RPermissions` 字节级互通，含会话吊销表）。检索证据：
  `Pek.ZPermissions/src/{jwt,secret,session,http_auth}.zig` 提供 `Builder.fromSecret` / `encodeObject` /
  `validate` / `Decoded` / `Keeper.{register,authorize,revoke}` / 四种 Store。
  唯一缺口是 `http_auth.Guard` **只认 `Authorization: Bearer`**，浏览器 Cookie 需在消费方补 ——
  本仓库在 `src/auth.zig` 里补「Cookie 优先、Bearer 次之」的取令牌逻辑，仍复用它的校验与吊销。
- **C# 参考工程没有可抄的鉴权实现**：`PekStartup.cs` 里 `UseAuthentication` / `UseAuthorization`
  只有注释，动作层仅 `[EntityAuthorize(PermissionFlags.Update)]`（框架内拦截）。所以 Zig 侧是**补实现**，
  不是移植（见 `docs/移植对照.md` 第 2 节第 9 条）。
- **默认不强制登录**（`requireLogin` 默认 `false`）：与 C#/Rust 现状一致，避免改动既有页面行为与冒烟断言；
  需要时一行开关即变成「后台页面未登录 → 302 到登录页并带 `returnUrl`」。
- **登出必须真的让令牌失效**：只删 Cookie 不算（令牌还能被 Bearer 重放），所以走 `Keeper.revoke`。

### 落地点

| 文件 | 变更 |
|---|---|
| `src/auth.zig`（新增） | `Auth.{init,deinit,issue,principal,tokenOf,logout,cookieHeader,clearedCookieHeader,withCookie,middleware,isGuardedPath}`；`Options`；`Principal`；`cookieValue`/`percentEncode` 工具；8 项单测 |
| `src/options.zig` | `Builder.{jwtSecret,jwtIssuer,jwtExpireMinutes,requireLogin,cookieSecure,sessionStore}`；`build()` 装配 `Auth` 并 `admin_area.setAuth` |
| `Areas/Admin/Controllers/AdminArea.zig` | 持有 `auth`；`mount` **最先**挂鉴权中间件；登录控制器新增 `logout`（POST+GET）与 `status` 路由 |
| `Areas/Admin/Controllers/LoginController.zig` | 登录成功签发 JWT（Ajax 返回 `token`/`tokenType`/`expiresIn`/`expiresAt`，两种响应都下发 `Set-Cookie`）；新增 `logout`（吊销 + 清 Cookie）、`status` |
| `Views/Shared/_Layout.cshtml` | 头部新增「退出」入口（`{areaRoute}/login/logout`） |
| `build.zig(.zon)` | 新增路径依赖 `.pek_zpermissions`；`paths` 补 `pek_zdsmallui.zig` / `Areas` / `Controllers` / `Views`（否则当作依赖被引用时缺文件） |

## 2026-11-19 口令与 C#/Rust 三方互通 + 前端 MD5 传输 + 浏览器实测

**用户原话**：
1. 「登录是支持md5加密传输，然后按默认的md5+sha1的方式做检验和存储的吧？」
2. 「密码规则和C#和Rust的一样的要相互之间能处理」
3. 「另外你要学G:\Code\Rust\HLZX.EIP自己打开相应的页面自己跑测试。要做功能和界面等验证」

### 一、口令规则：三方逐字一致（有 C# 实测证据）

| 环节 | 规则 | 证据 |
|---|---|---|
| 存储格式 | `$算法$盐$散列` | C# `IPasswordProvider.cs:83` / Rust `password.rs:132` / Zig `password.zig:hashWithSalt` |
| `md5+sha1` 计算 | `Base64(HMACSHA1(key=盐字节, msg=MD5原始16字节(明文UTF8)))` | C# `IPasswordProvider.cs:75`；Rust 注释 `password.rs:21`；Zig `compute(.md5_sha1)` |
| 盐 | 16 位随机，字符集 `a-zA-Z0-9./`；`SaltTime>0` 时用 Unix 秒 | C# `_cs`/`CreateSalt`；Zig `SALT_CHARSET`/`SALT_LENGTH` |
| 默认算法 | **`md5+sha1`**（C# 默认 `sha512` → 本仓库与 Rust 显式选 `md5+sha1`，否则丢掉前端 MD5 能力） | 本仓库 `DEFAULT_ALGORITHM` |
| 旧值兼容 | 明文 / 裸 MD5 十六进制（大小写不敏感）；登录成功自动升级为 `$md5+sha1$…` | C# `Verify` 老值分支；Zig `verifyAndUpgrade` |
| 前端 MD5 输入 | 允许把 32 位 hex 当作「已算好的口令」 | C# `Verify` 支路 3；Zig `hexDecode → HMAC` |

**C# 端实测**（`DH.RustBase\tools\csharp\DHRustDemo`，引用 `NewLife.Security.SaltPasswordProvider`）：

```text
password-hash-fixed md5+sha1 "New#life" "abCD12./xyZ9012Q"
  → $md5+sha1$abCD12./xyZ9012Q$FAXHeXyCpOSOPugOqcHia+ZVMOw=      # 与 Zig 输出逐字相同
password-hash-fixed md5      "中文口令123" "abCD12./xyZ9012Q"
  → $md5$abCD12./xyZ9012Q$BD5AD3872AB26F331056B0CB80328826      # 中文 UTF-8 也对得上
password-verify-alg md5+sha1 <md5(New#life) 小写>  → OK
password-verify-alg md5+sha1 <md5(New#life) 大写>  → OK
password-verify-alg md5+sha1 <别的口令的 md5>      → FAIL
```

这些数值已写进 `src/password.zig` 的 `CSHARP_GOLDEN`（5 种算法）与中文口令用例，
**任一侧改算法/编码/大小写，`zig build test` 立刻报警**（现 93/93）。

### 二、前端 MD5 传输

- 新增 `assets/login-md5.js`（标准 RFC1321，`TextEncoder` 取 UTF-8 字节，零第三方依赖），
  由 `materializeDefaults()` 落地到 `wwwroot/static/admin/js/login-md5.js`，登录页引用；
- 提交时把 `#Password` 明文替换成 **32 位小写 hex**（`dataset.md5` 防止重复散列）；
- 后端 `verify` 双分支：明文 / MD5 都收，**脚本没加载也能登录**（渐进增强）。

**浏览器实测**：`window.dsmalluiMd5('admin123')` = `0192023a7bbd73250516f069df18b500`
（与 `python hashlib` / C# 一致，中文口令同样一致）；提交瞬间字段值已是该 32 位 hex。

### 三、界面与功能实测（照 HLZX.EIP 的做法：起服务 → 打开页面 → 实点 → 截图）

| 场景 | 结果 |
|---|---|

### 四、本轮修掉的 4 个缺陷（都是实测才暴露）

1. **`Auth.principal` 返回悬垂切片**：`Decoded` 自带 arena，`defer decoded.deinit()` 后
   `user_name`/`display_name` 指向已释放内存 → 首页「当前用户」显示成二进制垃圾。
   改为把三个字段 `dupe` 到调用方 arena。
2. **登录页 `returnUrl` 未回填**：模板有 hidden 字段，但 `buildModel` 没给值 → 登录后恒去首页。
   `index` 现在从 `?returnUrl=` 读出并 `safeRedirect` 校验后回填。
3. **界面无样式**：视图用的 `admin-panel / admin-form-row / admin-alert / admin-card…` 在第三方
   `admin.css` 里根本不存在（那是 C# 工程的类名集合）。新增本仓库 `assets/admin-ui.css` 补齐，
   `_Layout` 在第三方样式之后引用，只补不盖。
4. **Prompt 页漏出孤立 `}`**：`@if (Model.autoBack) { <script>…function () {…}…</script> }` ——
   Razor 子集遇 `}` 即结束块，JS 被截断、页面上多出一个 `}` 且 `pageerror` 非空。
   改成 `<meta http-equiv="refresh" content="1;url=…">`（同一限制的又一处实证，已写进模板注释）。

### 五、回归

- `zig build test`：**93/93**（新增 3 项：C# 五算法黄金向量、中文口令、C# 生成的 `md5+sha1` 接受前端 MD5）；
- `tools/regression.ps1`：**25 项冒烟全 PASS，退出码 0**。新增 7 项：
  登录页含 `login-md5.js`、`returnUrl` 回填、`admin-ui.css` 可访问、`login-md5.js` 可访问、
  config 页引用内置样式、Prompt 页 meta refresh 自动返回、**MD5 口令登录 302**。
- 脚本清理清单补全为 `Views / Areas / admin-ui.css / login-md5.js / admin-config.js`，
  避免「只补缺失」造成旧副本掩盖新模板。

## 2026-11-19 HTTP/2 评估 + 静态资源流式确认（实测）

**用户原话**：「是不是要支持http2来提高并发？」「还有静态资源是不是已确定不会还走代码复制再输出这条路」

### 一、HTTP/2：本轮不上，先做 HTTP/1.1 keep-alive 才是性价比路径

事实核查：

1. **Zig 0.17 标准库没有 HTTP/2 服务端**：`lib/std/http/` 只有 `Client.zig`、`Server.zig`（HTTP/1.1）、
   `ChunkParser/HeadParser/HeaderIterator`，无 h2/HPACK；
2. `std.http.Server` **原生支持 HTTP/1.1 持久连接**：`RespondOptions.keep_alive`（默认 `true`）、
   `receiveHead()` 可循环调用（`Server.zig:306/325/351-363`）；
3. **zzig 目前主动放弃了 keep-alive**：`src/http/server.zig` 的 `buildHeaders` 强制
   `connection: close`，`connMain` 处理完一个请求即 `stream.close()`；且每连接 `std.Thread.spawn` 一个线程
   （`server.zig:124`），`max_connections` 默认 64。

实测（同一台机器，curl 单进程多 URL）：
- 静态资源 5.66 ms/req（含 TCP 建连 + 线程创建），而服务端业务处理仅 **1.06–2.33 ms** →
  **建连/线程占 60–80%**；
- 结论：当前并发瓶颈不在协议版本，而在「每请求建连 + 每连接建线程」。
  h2 需要长连接 + 单连接多路复用，**与 thread-per-connection 模型根本冲突**（要重写成事件驱动/协程），
  且 std 无实现（自写 HPACK/流控成本以周计），**收益远低于成本**。

建议顺序（按性价比）：

1. **HTTP/1.1 keep-alive**（std 原生支持，改造集中在 `server.zig`：`connMain` 循环 +
   去掉强制 `connection: close` + 空闲超时/最大请求数）→ 预计把静态 5.66 ms 拉回 1 ms 量级；
2. 线程池替代每连接 create（进一步降线程开销）；
3. **生产前置 nginx 终结 TLS/HTTP2**：浏览器 ↔ nginx 用 h2，nginx ↔ 应用走 1.1 keep-alive，
   Zig 侧不必实现 h2。

（keep-alive 改造属服务端架构变更，本轮未动；需要时按上述清单落地并用并发压测对比。）

### 二、静态资源：**已确定全程流式，不存在「读进内存再输出」**

- `StaticFiles.stream_threshold` 默认 **0**（`static_files.zig:89`）→ **所有磁盘文件都走流式**：
  命中后 `stat` → `openFile` → `Response.file`（`static_files.zig:534-546`）；
  只有把 `setStreamThreshold` 调大，小文件才会走 `readFileAlloc` 优化分支；
- 服务端：`Response.file` → `respondStreaming` + `writer.sendFile`
  （Linux 零拷贝；Windows 返回 `Unimplemented` → 回退 32 KB 缓冲读-写循环）；
- 本仓库下载：`UploadController` **直接复用** `StaticFiles.serve`（注释即「路径穿越防护 + ETag/304 + 流式发送」），
  只在响应头追加 `content-disposition`，**不读文件内容**；
- **实测**（`/Upload/downloads/bench/big100m.bin`，100 MB）：
  `size_download=104857600`、耗时 **0.096 s（≈1.04 GB/s）**，
  服务进程 WorkingSet **6.7 → 6.9 MB（峰值 8.3 MB）** → 确认没有整读进内存；
- 仍「在内存里」的只有：编译期嵌入资源（`statics.embed`）、视图渲染出的 HTML（KB 级），属设计预期。

## 2026-11-19 keep-alive 落地：瓶颈在 zzig 服务端（本轮已修）+ 连接上限修正

- **用户原话**：「瓶颈在 zzig 服务端的 `connection: close` + 线程模型，这个是不是要优化？性能优化肯定不只当前库，涉及到的库都要考虑。」
- 处理方式：**改公共库 zzig**，本库只跟着吃收益（不复制一份 server 实现）。

### 一、zzig 侧改动（`src/http/server.zig`）

1. 默认 HTTP/1.1 **keep-alive**：同一连接连续服务最多 `keep_alive_requests`（默认 100）个请求；
   `Options.keep_alive = false` 可退回短连接。
2. 可复用时下发 `keep-alive: timeout=5`；不复用时回 `connection: close`。
   **不做空闲硬超时**（`std.Io.net.Stream` 无 read-timeout API），空闲超时交给前置反代，长连接由请求数封顶。
3. 每个响应后显式 `flush()`（keep-alive 下不能靠「关连接时刷」）。
4. `max_connections` 默认 **64 → 512**（浏览器同域 6 连接，64 会让面板在正常并发下白屏）。

### 二、本库实测（`/biz/login/index` 模板渲染，.NET `HttpClient` 串行，warmup 10）

| 请求数 | keep-alive | `Connection: close`（旧行为） | 加速比 |
|---|---|---|---|
| 200 | 185.1 ms（1080.8 rps） | 456.7 ms（437.9 rps） | **2.47×** |
| 500 | 476.3 ms（1049.7 rps） | 1039.4 ms（481.1 rps） | **2.18×** |

服务端 RSS 7.1 MB。curl `-v` 两次请求均为 `Connection #0 ... left intact` → 确认复用同一条连接。

### 三、验证

- zzig `zig build test` → **232/232**（新增 3 个真 socket keep-alive 用例）。
- 本库 `tools/regression.ps1` → **FAIL=0**（28 项冒烟全 PASS，含登录/JWT/伪静态/上传下载/Prompt）。

### 四、线程模型：结论与后续

- 本库与 zzig 的 HTTP 服务端仍是**每连接一线程**。keep-alive 只延长连接寿命、由请求数封顶，不会像 SSE 那样永久占线程；
  但上千**长连接**不能靠调大 `max_connections` 硬扛（线程 O(n)）。
- zzig 已有事件循环范式（`ConnDispatch.task` + `std.Io` 后端），HTTP 侧对齐需单独一轮（含 232 项回归），
  本轮先做 keep-alive，避免同时动两处。
- HTTP/2 仍不适用（std 无服务端 HPACK 实现），生产建议前置 nginx 终结 h2。

### 五、坑

- 回环测试里「写请求 → 读响应 → 再写请求」的时序会阻塞在第一次读；改成一次性 pipelining 后通过。
  curl / .NET HttpClient 对同一服务完全正常 → 是**测试驱动写法**的问题，不是服务端行为。

## 2026-11-19（六）异步高并发落地：zio 运行时 + `dispatch = .task`（5000 连接 / 32 线程）

- **用户要求**：「**不能每连接一线程**」、「**必须要考虑异步高并发。我们的项目是百万级的**」，
  并提示「**grpc 这个项目不是有实现过类似的么？**」—— 按提示去读 zgrpc，而不是自造。

### 侦察结论（复用优先）

- zgrpc 的 `examples/with-zio/main.zig` 已给出完整接入方式：**zio 完整实现 `std.Io`**，
  所以 zzig 的 HTTP 代码**一行都不用改**，只改两处：
  ① `io` 用 `rt.io()`（`zio.Runtime.init(...)`）；② `dispatch = .task`。
- `std.Io` 自带的事件循环后端在本版本**不可用**：`Evented` 在 Windows 是 `void`（无后端），
  在 Linux 是 `Uring`，但 `std/Io/Uring.zig` 引用了 `Io.Operation` 里不存在的 `net_accept`
  → `zig run` 直接编译失败（实测）。**所以必须用 zio**，不能用 std 自带后端。
- 另一个坑：`compat.currentIo()` 返回的是 `Threaded.global_single_threaded.io()`（**单线程 io**），
  所以之前 `.task` 必然报 `ConcurrencyUnavailable` 退回线程 —— 这解释了「为什么一直是每连接一线程」。

### 接入（本库 `examples/zio_server.zig` + `zig build zio-server`）

```zig
const rt = try zio.Runtime.init(gpa, .{
    .executors = .auto,
    .stack_pool = .{ .maximum_size = 1024 * 1024, .committed_size = 16 * 1024 },
});
const io = rt.io();
var srv = zzig.http_server.Server{ .gpa = gpa, .io = io, .ctx = ..., .handler = handle,
    .opts = .{ .dispatch = .task, .max_connections = 200_000 } };
var group: std.Io.Group = .init;
group.async(io, runServer, .{ &srv, "127.0.0.1", port });   // 必须在运行时里起
group.await(io) catch {};
```

**两个必须记住的坑**：
1. **不能把 `Server.run` 放到裸 `std.Thread` 里**（zio 的 accept/读写只在运行时上下文挂起协程，
   跑到外部线程会卡死）—— 用 `std.Io.Group.async` 起。
2. **栈池要调小**：zio 默认每协程提交 256 KiB → 上万连接就是几 GB；连接协程栈用量很小
   （收发缓冲都在堆上），降到 **16 KiB 提交 / 1 MiB 上限**。

### 实测（本机 Windows 11 + zig 0.17.1 + zio 0.20.1）

| 模型 | 连接数 | 服务端线程 | 工作集 |
|---|---|---|---|
| std（每连接一线程，`max_connections=4096`） | 700 | **703** | 79.1 MB |
| **zio + `dispatch=task`** | **5000** | **32** | **7.6 MB** |

- 5000 条 keep-alive 连接：**第 1 轮 5000/5000 成功、第 2 轮复用 5000/5000 成功**
  （2.8s + 复用全成功 → 证明 5000 条连接被服务端**同时持有**，不是排队）。
- 全程线程 32 不变、工作集 7.6 MB 不变、断开后仍 32 → **线程数与连接数彻底解耦**。
- 注意：`Get-Process` 的 `HandleCount`（172）**不随连接增长**，不能拿它当指标；
  可靠指标是 `netstat` 的 ESTABLISHED 数（5000 连接 → 10000 条）+ 第二轮复用成功率。

### 口径（重要，别误读）

- **Windows 上吞吐并不更快**：zgrpc 实测 std 每连接一线程在低并发下 QPS 更高
  （1 连接 4762 vs 2502）。异步模型的收益在**连接数**，不在单连接吞吐。
- 因此本库**默认仍走 std 线程模型**（`zig build run`），需要大规模并发时用 `zig build zio-server`。
- **百万级还需做的**：① Linux 上用 io_uring 复跑同一份代码（Windows 只有 IOCP，行为不同）；
  ② 系统层调参（`ulimit -n`、`somaxconn`、`tcp_max_syn_backlog`、`nf_conntrack_max`）；
  ③ 2 万 / 5 万 / 10 万连接逐级压测，确认内存与 fd 曲线；④ 横向扩容（单机百万本就不是常规做法）。

## 2026-11-19（七）小规格服务器（2 核 / 4 核）实测：线程自动按核数，瓶颈是内存不是线程

- **用户问题**：「服务端线程是自动扩充的吧？因为服务器上一般都是 2 核 4G 或者 4 核 8G 之类的」。

### 源码依据（zio `src/runtime.zig:126`）

```zig
fn autoDetect() u8 {
    const affinity = @min(Executor.max_executors, std.Thread.getCpuCount() catch 1);
    // 也尊重 cgroup CPU 配额（Docker/K8s），类似 Go 的容器感知 GOMAXPROCS
    const limit = cgroup.cpuLimit() orelse return @intCast(affinity);
    return @intCast(@min(affinity, @as(usize, limit)));
}
```

→ `executors = .auto` **就是按 CPU 核数**（并尊重 cgroup 配额），所以：
**2 核 → 2 个 executor，4 核 → 4 个**，容器里也正确。不需要手工配。

### 实测（本机用 `executors=2` 模拟 2 核，其余不变）

服务入口支持第 2 个参数：`zig build zio-server -- <port> <executors>`
（`executors=0`/缺省 = `.auto`；用小数值可以在大机器上模拟小规格服务器）

| 指标 | 32 核（`.auto`） | **2 executor（模拟 2 核）** |
|---|---|---|
| 空载线程 | 34 | **2** |
| 5000 连接时线程 | 32 | **5** |
| 空载工作集 | 7.6 MB | 6.4 MB |
| **5000 连接时工作集** | 7.6 MB | **562.1 MB** |
| 第 1 轮 5000 请求 | 5000/5000 | **5000/5000**（3.8s） |
| 第 2 轮复用 | 5000/5000 | **5000/5000** |
| 断开后线程 | 32 | 6（回落） |

### 结论（对小规格服务器的实际意义）

1. **线程数不用管**：按核数自动定，2 核就是 2~5 个线程，**连接数不跟线程数挂钩**（5000 连接照样全成功）。
2. **真正的瓶颈是内存**：2 executor 下 5000 连接占 **562 MB**（≈112 KB/连接）——
   因为并发协程多、可复用的线程少，协程栈没法像 32 线程时那样被快速复用回收。
   **4 GB 机器按此推算约 2~3 万连接**（要留余量给业务 handler 与缓存）。
3. **CPU 决定吞吐**：2 executor 下 loopback 单连接串行 **31182 rps**（0.03 ms/请求），
   真实网络 + 业务逻辑会显著更低；4 核大致线性提升。
4. 若要进一步压低每连接内存：调小 `stack_pool.committed_size`（现 16 KiB）、
   缩短 `keep_alive_requests`（及时释放协程），或给小规格机器配 `max_connections`。

## 2026-11-19（八）每连接 123 KB 内存的分解与优化（用户问「怎么会占用这么多内存」）

- **现象**：2 executor（模拟 2 核）下 5000 连接占 **601 MB**（123 KB/连接），而 32 核下同样连接数只 7.6 MB。
- **排除实验（都是实测）**：
  1. **不是栈数组**：`serveWithLimit` 里两个 16 KiB `uvar` 改为 `gpa.alloc` 堆分配 → 内存**几乎不变**（601 MB）。
  2. **不是 `committed_size`**：16 KiB → 128 KiB，工作集**完全不变**（601.2 MB），只有私有提交从 698 → 932 MB
     → 说明这是每协程实际触碰的物理内存，与栈提交配置无关。
  3. **不是 zio 协程**：新增 `examples/minaccept.zig`（只 accept + 读一个字节，不解析 HTTP）
     → 同样 5000 连接只 **88.3 MB（18.1 KB/连接）**。
- **分层结论（5000 连接，2 executor，Windows 11）**：

  | 阶段 | 每连接 | 5000 连接 |
  |---|---|---|
  | ① 纯 accept + read（zio 协程底噪） | **18 KB** | 88.3 MB |
  | ② + `std.http.Server.receiveHead` + 头迭代（不响应） | **70 KB** | 342.4 MB |
  | ③ + respond / arena / 我方头复制（完整 zzig HTTP） | **123 KB** | 601.2 MB |
  | ④ 同上但缓冲 4 KiB/4 KiB | **98 KB** | 479.3 MB |

  → **zio 只占 18 KB；大头是 `std.http` 的解析（+52 KB）与我们自己的响应/arena 层（+53 KB，其中缓冲 24 KB 可配）。**

- **已落地优化**：
  - `zzig.Options.conn_recv_buf_size` / `conn_send_buf_size`（默认 16 KiB，**堆分配**而非栈数组）；
    上万连接场景设 **4 KiB**（实测省 25 KB/连接）。
  - `examples/zio_server.zig` 默认已用 4 KiB/4 KiB。
  - 缓冲从栈搬到堆：虽然工作集没变，但**消除了「栈必须扩容到 32 KiB 以上」的隐患**（否则调小 committed 会踩栈溢出）。
- **4 GB 机器的实际估算**：按 98 KB/连接 → 理论 4.2 万，留余量给业务 handler/缓存 → **约 3 万连接**。
- **下一步（若还要压）**：① 把 `std.http` 的解析换成自写轻量解析（能砍掉那 52 KB，但工程量大）；
  ② **在 Linux 上复验**（Windows 的栈/分配粒度偏大，io_uring 侧数字应更低）。
- **诊断工具保留**：`zig build minaccept -- <port> <executors> [http]`（`http` 加解析），用于以后复现这组分解。

## 2026-11-19（九）与 C# / Rust 的每连接内存横向实测（用户问「理论上也是同样占用么」）

- **结论先给**：**不一样，而且差 4~5 倍**。同样 5000 个空闲连接（connect 后一个字节都不发）：

  | 实现 | 空载 | 5000 连接 | 增量 | **每连接** |
  |---|---|---|---|---|
  | C# Kestrel（`.NET 11`，Release） | 42.9 MB | 98.0 MB | 55.1 MB | **11.3 KB** |
  | Rust hyper + tokio（`dhrust` spa_server，dev） | 8.2 MB | 77.5 MB | 69.3 MB | **13.9 KB** |
  | Zig `zio` + `std.http`（ReleaseFast，128 KiB 栈上限） | 5.5 MB | 302.7 MB | 297.2 MB | **59.3 KB** |
  | Zig `zio` + `std.http`（Debug，128 KiB 栈上限） | 6.3 MB | 401.1 MB | 394.8 MB | 80.2 KB |
  | Zig `zio` + `std.http`（Debug，1 MiB 栈上限） | — | 479.3 MB | — | 98.2 KB |
  | Zig 只 accept+read，不解析（`minaccept`） | 3.4 MB | 88.3 MB | 84.9 MB | **18.1 KB** |

  命令：C# `dotnet <dll>` + Python 按住 5000 连接；Rust `target\debug\examples\spa_server.exe 18111`；
  Zig `zig build zio-server [-Doptimize=ReleaseFast] -- <port> 2`；客户端统一 `tools/_hold_conns.py`。

- **差异根源是协程模型，不是「我们写得差」**：
  - C# / Rust 用**无栈协程**（`async` 状态机 / tokio task），每连接的「挂起点状态」放在**堆上的小结构里**，
    栈是工作线程共享的固定栈 → 每连接只需 **几 KB ~ 十几 KB**。
  - Zig `zio` 是**有栈协程**，每条连接有独立协程栈；栈要能容纳**同步调用链的最深路径**。
    而这条路径上坐着 `std.http.receiveHead`（+ 我方 `handleOne`），**实测需要 > 64 KiB**。

- **栈下限是实测出来的（不是猜）**：
  - `maximum_size = 64 KiB` → **第 130 个连接就 `Stack overflow`**（Debug 与 ReleaseFast 都复现；
    Debug 下更早，第 3 个连接就崩）。
  - `maximum_size = 128 KiB` → 正常跑满 5000 连接。
  - 所以 **128 KiB 是「用 `std.http`」的硬成本**，调不下去。

- **优化空间与代价**：
  - `1 MiB → 128 KiB`：98.2 → 80.2 KB/连接（Debug），省 18 KB/连接（5000 连接省 78 MB）。
  - `Debug → ReleaseFast`：80.2 → 59.3 KB/连接，省 21 KB/连接（Debug 栈帧大，`std.http` 的结构体按值返回、内联不足）。
  - **要再往下只有一条路**：不用 `std.http` 的 head 解析，自己写轻量解析（状态机放堆上、栈需求降到 16~32 KiB），
    理论上能逼近 20~25 KB/连接 —— 也就是 C#/Rust 的 2 倍以内。代价是要重写并重跑全部 HTTP 用例。

- **口径说明（避免误读）**：
  - 三者都是**空闲长连接**（只 TCP 握手，不发请求）；一旦开始收发，还要加 body 缓冲，但 body 是按需分配的。
  - C# 是 `.NET 11` Release；Rust 是 dev（未开优化）；Zig 两种优化档都给了 —— 拿 ReleaseFast 那行对比才公平。
  - Windows 的分配粒度/栈粒度偏大，**Linux（io_uring）上 Zig 侧数字应更低**，仍需复验。

- **对「百万连接」的结论**：C#/Rust 走「无栈协程 + 堆状态」路线，量级上更接近百万；
  Zig 侧要保持 `std.http`，每连接 ~60 KB（ReleaseFast）算，10 万连接约 6 GB、百万连接需 60 GB —— **不现实**。
  若目标真是百万，必须先做自写解析（~20 KB/连接 → 百万 20 GB，仍需分片部署）或改走「少量长连接 + 多路复用」。

- **用户原话**：「C#和Rust的从理论上来说也是同样的内存占用么？」

- **纠正记录**：本轮先说「Rust 每连接固定 64 KiB 缓冲（`http.rs:283`）」——**错了**，
  那行在 `FileStreamBody::new` 里，是**文件流响应用的**，与连接缓冲无关。Rust 每连接的开销来自 hyper 的按需缓冲 + tokio task。

## 2026-11-19（十一）HTTP 接入层换成 lighting 的自写解析：每连接 59.3 → 20.9 KB

- **用户决定**：「那就http相关的全部换lighting项目吧？」

- **落地边界（重要，避免误读）**：换的是**HTTP 接入层**（`zzig/src/http/server.zig` 的协议解析与响应写入），
  **不是** `router` / `controller` / `view` / `static_files` / `web` —— 那些是 zzig 自己的业务层能力，
  lighting 里没有对应实现（它只有 Go 风格的 `ServeMux`，没有 Razor 子集视图、控制器注册、组件体系）。
  换掉它们等于把生态能力砍掉，不是这次的目标。

- **具体做法**：`zzig` 增加 path 依赖 `../lighting`，只借三样东西：
  1. `parseRequestHead`（零拷贝请求行/头校验，给出 method/target/content_length/is_chunked/keep_alive）；
  2. `BodyReader`（Content-Length 与 chunked 解码）；
  3. 无 —— 响应仍由本库自己组装（`buildHeaders` / `buildHeadersWithLength` / `writeHead`），
     因为要保住 **`early_guard`（头阶段 403/413 不读 body）**、**`sendFile` 零拷贝**、安全头与 keep-alive 语义。
  `lighting` 的 `HeaderMap` **没有遍历接口**（只有 get/set/add/getAll），所以请求头列表由本库按原始字节扫一遍
  （`head_bytes` 已通过 `parseRequestHead` 的格式校验，二次扫描安全、零额外分配），名字统一转小写。

- **踩到的第二个「栈数组」坑（这是本轮最大发现）**：
  - 改完解析后，5000 空闲连接仍是 **52.9 KB/连接**（与 128 KiB / 32 KiB 栈上限无关），而 lighting 版只要 20.4 KB。
  - 根因：`handleOne` 文件响应分支里的 `var read_buf: [32 * 1024]u8` 是**栈数组** —— Zig 在函数入口就为它
    预留栈，即使走的是非文件分支。改成 `gpa.alloc` 后立刻降到 **20.9 KB/连接**。
  - 教训：**协程里任何 `var x: [N*1024]u8` 都等于给每个连接加 N KiB**，必须堆分配（与（八）节 `serveWithLimit`
    的两个 16 KiB 数组是同一类问题）。

- **实测（5000 / 4000 空闲连接、2 executor、ReleaseFast、4 KiB 收发缓冲、32 KiB 协程栈）**：

  | 版本 | 连接数 | WS | **每连接** |
  |---|---|---|---|
  | `std.http` + 128 KiB 栈（改造前） | 5000 | 302.7 MB | **59.3 KB** |
  | lighting 解析 + 128 KiB 栈 | 5000 | 263.6 MB | 52.9 KB |
  | **lighting 解析 + 32 KiB 栈 + read_buf 堆分配** | **4000** | **87.2 MB** | **20.9 KB** |

  与横向基线对齐：C# Kestrel 11.3 KB / Rust hyper+tokio 13.9 KB / lighting 原生 20.4 KB。**差距从 5 倍收到 1.5~1.8 倍。**

- **真实请求路径验证（不能只看空闲连接）**：`tools/_http_load.py` 让每个连接发一个完整 GET 并断言 200 ——
  **1500 个请求全部 200、0 失败**，32 KiB 协程栈在完整「解析 → 业务 → 响应」链路上不溢出。

- **回归**：
  - zzig：`zig build test` → `zzig-module-tests 213 pass` + `zzig-tests 25 pass` + `xml-tests 27 pass`，全绿；
    其中 HTTP 相关用例 **67 项**（含 web 控制器、静态资源流式桥接、gzip、405、500）。
  - 本库：`tools/regression.ps1` → **99 单测 + 35 项冒烟全 PASS（FAIL=0）**，
    含「150 个小头 → 431」「20 个小头 → 200」、WAF 拦截/不误伤、XFF、登录与上传。

- **已知行为收窄（如实记录）**：
  - `QUERY` 方法：`std.http.Method` 有、lighting 的 `Method` 没有 → 收到会回 400（生态里没有使用者）。
  - chunked 请求体读完不复用连接（与原实现口径一致：`transfer-encoding != none` 时 `keep = false`）。
  - `Options.conn_send_buf_size` 仍生效（响应写入走本库的 `stream.writer`），未改动。

- **下一步（未做）**：Linux（io_uring）复验；自写解析后 `header_timeout_ms` 是否能在 POSIX 上安全启用的复测。

  - 运行期连接改用 `sqlite.Db.openWithOptions(..., .{ .journal_mode = "WAL", .synchronous = "NORMAL",

  - `Data/Biz.db-wal` + `Biz.db-shm` 文件已生成 → WAL 确认生效；

  - `cache_size` / `mmap_size`：面板数据量在 MB 级，收益不抵复杂度 → 不做；

- **HTTP 侧结论**：头层面已到平台期（Windows 21279 rps @2 核 / Linux 61976）。

## 2026-11-22 配置键大小写（`COLLATE NOCASE`）导致「保存成功却回读不到」

- **现象**：`tools/regression.ps1` 冒烟里 `POST /biz/config/updatebase` 返回 200，
  但随后读 `/biz/config/index`（或 `/biz/home/dashboard`）拿不到新值，站点名恒为空。
- **实测证据**（直接读示例库 `.zig-cache/zdsmallui-example/Data/Biz.db`）：
  - `Config` 表定义是 `"Name" nvarchar(100) COLLATE NOCASE`（C# `Model.xml` 同源）＋ `UNIQUE(Name)`；
  - 库里实际存的是 **camelCase** 行：`siteName = 'PromptCheck'`、`seoTitle = 'RegressionTitle'`；
  - `select count(*) from Config where Name='SiteName'` = 1 —— **但那一行的 Name 字面是 `siteName`**
    （NOCASE 比较命中），说明键在库里的写法与代码期望的写法不一致。
- **根因（三层叠加）**：
  1. `putSettingLocked("SiteName", …)` 先 `count(Name='SiteName')` → NOCASE 命中历史 `siteName` 行 →
     走 `updateOne(Value)` → **只更新值、Name 保持 `siteName`**；写入侧永远产生不了 PascalCase 行；
  2. `normalizeConfigKeys()`（camelCase → PascalCase）同样用 `count(Name='SiteName') > 0` 判「新键已存在」→
     在 NOCASE 库上**恒为真** → 永远不会改名（在大小写敏感的方言上才生效）；
  3. `settingsImpl()` 建 map 用**实际存储的 Name** 作键（`siteName`），而 `settingsValue()`
     用 `DEFAULT_SETTINGS.store_key`（`SiteName`）精确查 → **查不到 → 回落到默认空串**。
- **修法（不猜、两侧都收紧）**：
  - `backend.zig` 新增 `pub fn canonicalStoreKey(key)`：把 `siteName` / `SiteName` 统一归一成
    `store_key`（`SiteName`），白名单外的键（`__configVersion` 等元数据）原样返回；
  - `sqlite_backend.zig` 的 `getSettingLocked` / `putSettingLocked` 读写前都过一次 `canonicalStoreKey`；
  - `settingsValue()` 增加大小写无关兜底 `lookupSettingIgnoreCase`（先精确、再 `eqlIgnoreCase` 遍历），
    这样历史 camelCase 行也照样读得到 —— **不要求运维手工改库**。
- **为什么不「把库里的键统一改名」**：`Config.Name` 是 NOCASE，改名在 SQLite 上无法与「新旧键并存」区分，
  且历史库可能两行并存；读取侧大小写无关 + 写入侧归一，是唯一在**大小写敏感/不敏感方言上行为一致**的做法。
- **护栏**：`src/sqlite_backend.zig` 单测新增「控制器链路」用例 ——
  `backend().saveSettings(form)` 后必须 `setting("SiteName")` / `setting("SeoTitle")` 都读到新值，
  且 `__configVersion` 已递增（这条用例在修复前必然失败：只 bump 版本、读回为空）。
- **回归断言同时纠正两处「断言对象写错」**（不是为变绿改断言）：
  - `GET /biz/home/index` 是**框架页**（顶部 + 左侧 + iframe），不含「快捷入口」文案 →

## 2026-11-23 后台页统一 `Cache-Control: no-store`（「语言包键怎么还是没变」的真因）

- **用户原话**：「后台语言包资源键怎么还是没有变？我前面不是提过要按C#那样弄么？」

  - 服务端返回的 `/admin/languages/index` HTML 第一列就是 `<td><code>menu.console</code></td>`

  18090 实测（登录 → 语言包页）缓存头与首列键均正确。
- **给用户的操作提示**：已打开的旧标签页仍会用内存里的旧文档，需**强刷一次**（`Ctrl+F5`）或重开标签；

## 2026-11-23 后台页脚「计算 / 渲染」两段耗时

### 用户诉求

前台每页底部早就有「服务端耗时」，后台只有「渲染」一段，看不出**取数慢**还是**模板慢**。
用户本轮打开 `Areas/Admin/Controllers/HomeController.zig` 追问后台这块，遂补齐。

### 做法

- `guarded()`（所有后台动作的唯一入口）里把 `request_started_ms` 写进 **threadlocal**；
- `renderView()` 里再取一次时间作为「渲染」起点，渲染完取第三次：
  - **计算** = 守卫入口 → 开始渲染（含区域校验、RBAC、鉴权取数、模型装配）；
  - **渲染** = 视图模板自身。
- layout 底部两个占位注释 `<!--calc-ms-->` / `<!--render-ms-->`，用 `injectTimings()` 一次替换；
  占位缺失（`Layout = null` 的独立页，如框架页 `Home/Index`）时原样返回，不做多余分配。
- 用 threadlocal 而不是往 `Ctx` 里加字段：zzig 是 thread-per-connection，一个线程同一时刻只跑一个请求，
  既不会跨请求串号，也不侵入框架的 `Ctx` 结构。

### 实测（`/admin/home/dashboard`，Windows）

```
计算 84~86 ms · 渲染 2 ms     ← 仪表盘：sysinfo 采集（进程/线程快照、磁盘）占大头
计算 1 ms    · 渲染 4 ms      ← /admin/config/index
```

结论：这个数字**立刻暴露了仪表盘的真实成本** —— 慢在取数（sysinfo），不在模板；
以前只有「渲染 2 ms」会让人误以为整页很快。

### 影响面

`Pek.ZDsMallUI` 目前的 Zig 消费方只有 `Pek.ZTools`；`Layout = null` 的页面不受影响。
回归：库单测 **107/107**，Pek.ZTools 一键回归 **PASS（0 失败）**。

### 追加：资源占用不需要实时 + 启动时间时区修正（同日）

用户原话：**「这个就不需要实时获取资源占用吧」**。

- **整份快照缓存 30 秒**（`sysinfo.collect`）：代价最高的是 Windows 的
  `CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD)` —— 它是**系统级**快照，要把全机线程枚举一遍
  才能筛出本进程的，本机实测 ~85 ms；其余 API（进程时间 / 内存 / 句柄 / IO）都是微秒级。
  实测：仪表盘首次 `计算 88 ms`，随后 `计算 0 ms`（30 秒内命中缓存）。
- **运行时长不进缓存**：用缓存里的进程启动时刻现算，任何时刻刷新都是准的；
  CPU% 本来就是「累计 CPU / 运行时长」的平均值，缓存不会让口径变化。
- 缓存用原子变量（`std.atomic.Value`）而非锁：偶发并发刷新只是多采一次，结果仍正确
  （Zig 0.17 的 `std.Thread.Mutex` 已并入 `std.Io`）。
- **顺带修一个真 bug**：仪表盘「启动时间」原来用 `std.time.epoch` 格式化，那是 **UTC**，
  注释却写「本地时区」—— 东八区机器上显示 `04:00` 而实际是 `12:00`。
  现在 Windows 走 `SystemTimeToTzSpecificLocalTime`（含夏令时、无需 libc），
  其它平台退回 UTC 并显式标注 `UTC`，不再假装是本地时间。
  实测修复后：`启动时间 2026-11-23 12:02:38`（`Get-Date` 12:02:40）✓

回归：库单测 **108/108**。
